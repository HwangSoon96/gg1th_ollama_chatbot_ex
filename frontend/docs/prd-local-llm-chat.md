# PRD: Local LLM Chat 프론트엔드

작성일: 2026-09-22
상태: 승인 대기 (1단계 / 3-파일 시스템)
범위: `frontend/` 만. 백엔드(`backend/`)는 수정하지 않는다.

---

## 1. 개요 (Introduction / Overview)

로컬에서 구동되는 Ollama 모델과 대화하는 웹 채팅 UI를 만든다.
FastAPI 백엔드(`POST /chat`, `GET /models`)는 이미 동작하며 **변경 없이 그대로 사용**한다.

현재 `frontend/`는 Vite + React 19 기본 템플릿 상태이며 실제 화면은 없다.
이 PRD는 템플릿을 걷어내고 실사용 가능한 채팅 앱을 구현하는 것을 목표로 한다.

해결하려는 문제: 로컬 모델을 쓰려면 터미널에서 `ollama run`을 쳐야 하고,
모델·시스템 프롬프트·샘플링 파라미터를 바꿔가며 실험하기가 번거롭다.
브라우저에서 파라미터를 조절하며 바로 결과를 비교할 수 있게 한다.

---

## 2. 목표 (Goals)

1. 로컬 Ollama 모델과 브라우저에서 대화할 수 있다.
2. 모델 / 시스템 프롬프트 / temperature / top_p / num_predict를 UI에서 조절하고
   그 결과 차이를 즉시 확인할 수 있다.
3. 응답 소요 시간(`elapsed_time`)과 사용된 모델을 응답마다 확인할 수 있다.
4. 설계도(`chat_ui_설계도.jpg`)의 정보 구조는 유지하되, UI/UX 완성도는 그보다 높인다.
5. 백엔드 API 계약을 1바이트도 바꾸지 않고 동작한다.

---

## 3. 사용자 스토리 (User Stories)

- **US-1** 사용자로서, 입력창에 질문을 입력하고 Enter를 눌러 모델 응답을 받고 싶다.
- **US-2** 사용자로서, 응답을 기다리는 동안 요청이 진행 중임을 명확히 알고 싶다.
- **US-3** 사용자로서, 설치된 모델 목록에서 원하는 모델을 골라 같은 질문을 다시 던져
  모델별 품질·속도를 비교하고 싶다.
- **US-4** 사용자로서, 시스템 프롬프트를 바꿔 모델의 말투와 역할을 조정하고 싶다.
- **US-5** 사용자로서, temperature / top_p / num_predict를 조절해 창의성과 길이를
  통제하고 싶다.
- **US-6** 사용자로서, 백엔드나 Ollama가 꺼져 있을 때 무엇이 잘못됐고 어떻게 고치는지
  알고 싶다. (조용한 실패 금지)
- **US-7** 사용자로서, 실수로 새로고침해도 방금까지의 대화가 남아 있으면 좋겠다.
- **US-8** 사용자로서, 모델 답변을 복사해서 다른 곳에 붙여넣고 싶다.
- **US-9** 사용자로서, 코드가 포함된 답변을 읽기 좋게 보고 싶다.
- **US-10** 사용자로서, 대화를 초기화하고 새 주제로 시작하고 싶다.

## 4. 기능 요구사항 (Functional Requirements)

### 4.1 채팅 (핵심)
1. 시스템은 사용자가 텍스트를 입력하고 전송할 수 있는 입력창을 제공해야 한다.
2. 시스템은 Enter로 전송, Shift+Enter로 줄바꿈을 지원해야 한다.
3. 시스템은 입력 내용에 따라 입력창 높이를 자동 확장해야 한다 (최대 높이 제한 있음).
4. 시스템은 전송 시 사용자 메시지를 즉시 대화 목록에 추가해야 한다 (낙관적 렌더링).
5. 시스템은 `POST /chat`에 `{message, model, system_prompt, temperature, top_p, num_predict}`를
   전송해야 한다.
6. 시스템은 응답 `{model, message, elapsed_time}`을 AI 메시지로 렌더링해야 한다.
7. 시스템은 응답 대기 중 전송 버튼을 비활성화하고 로딩 상태를 표시해야 한다.
8. 시스템은 새 메시지가 추가되면 대화 영역을 자동으로 맨 아래로 스크롤해야 한다.
   단, 사용자가 위로 스크롤해 과거 내용을 읽는 중이면 강제 스크롤하지 않는다.
9. 시스템은 대기 중인 요청을 사용자가 취소할 수 있어야 한다 (`AbortController`).
10. 시스템은 대화 초기화 버튼을 제공해야 한다. 초기화는 되돌릴 수 없으므로 확인을 거친다.

### 4.2 대화 맥락 (백엔드 제약 대응)
11. 백엔드 `/chat`은 **단일 message만 받고 대화 히스토리를 저장하지 않는다.**
    따라서 기본 동작은 "매 요청이 독립적인 단발 질문"이다.
12. 시스템은 "이전 대화 이어가기" 토글을 제공해야 한다. 켜면 최근 대화 N턴을
    `message` 문자열 안에 대화록 형태로 접어 넣어 전송해 맥락을 유지한다.
    (백엔드 수정 없이 가능한 유일한 방법)
13. 토글이 꺼져 있을 때 사용자는 이전 맥락이 전달되지 않는다는 것을 UI에서 알 수 있어야 한다.

### 4.3 모델 및 파라미터
14. 시스템은 앱 시작 시 `GET /models`로 설치된 모델 목록을 불러와야 한다.
15. 시스템은 모델 목록 로딩 실패 시에도 앱이 동작해야 한다 (수동 입력 또는 기본값 사용).
16. 시스템은 모델 선택 UI를 제공해야 한다.
17. 시스템은 임베딩 전용 모델(`bge-m3` 등 채팅 불가 모델)을 목록에서 제외하거나
    선택 불가로 표시해야 한다.
18. 시스템은 시스템 프롬프트를 편집할 수 있는 textarea를 제공해야 한다.
19. 시스템은 temperature(0~2), top_p(0~1), num_predict(1~2048)를 조절하는 컨트롤을
    제공해야 한다. 범위는 백엔드 `schema.py` 제약과 정확히 일치해야 한다.
20. 시스템은 각 파라미터가 무엇을 바꾸는지 짧은 설명을 제공해야 한다.
21. 시스템은 파라미터를 기본값으로 되돌리는 방법을 제공해야 한다.
22. 시스템은 설정(모델·프롬프트·파라미터)을 localStorage에 저장해 재방문 시 복원해야 한다.

### 4.4 메시지 표시
23. 시스템은 사용자 메시지와 AI 메시지를 시각적으로 구분해야 한다.
24. 시스템은 AI 메시지에 모델명과 응답 시간을 표시해야 한다.
25. 시스템은 AI 메시지에 복사 버튼을 제공하고 복사 완료 피드백을 보여줘야 한다.
26. 시스템은 답변 내 코드 블록을 고정폭 글꼴과 구분된 배경으로 렌더링해야 한다.
27. 시스템은 답변의 줄바꿈과 문단을 보존해 렌더링해야 한다.
28. 시스템은 대화가 비어 있을 때 빈 화면 대신 시작을 유도하는 화면을 보여줘야 한다.

### 4.5 오류 처리
29. 시스템은 백엔드 연결 실패 / 500 응답 / 타임아웃을 구분해 사용자에게 알려야 한다.
30. 오류 메시지는 원인과 다음 행동을 함께 제시해야 한다.
    예: "백엔드에 연결할 수 없습니다. `backend/`에서 `uv run main.py`를 실행하세요."
31. 시스템은 실패한 요청을 재시도할 수 있어야 한다.
32. 시스템은 오류 발생 시 사용자가 입력한 내용을 잃지 않아야 한다.

### 4.6 지속성
33. 시스템은 대화 내역을 localStorage에 저장하고 새로고침 시 복원해야 한다.
34. 저장 용량 초과 시 오래된 메시지부터 버리되 앱이 깨지지 않아야 한다.

### 4.7 품질 기준 (Quality Floor)
35. 시스템은 모바일(360px)부터 데스크톱까지 반응형으로 동작해야 한다.
36. 시스템은 키보드만으로 전체 조작이 가능해야 하며 포커스 링이 보여야 한다.
37. 시스템은 스크린리더를 위해 응답 도착을 알려야 한다 (`aria-live`).
38. 시스템은 `prefers-reduced-motion`을 존중해야 한다.
39. 시스템은 다크 모드를 지원해야 한다 (OS 설정 추종 + 수동 전환).
40. 본문 대비는 WCAG AA(4.5:1) 이상이어야 한다.

## 5. 범위 밖 (Non-Goals / Out of Scope)

- 백엔드 코드 수정 (`backend/` 전체) — 절대 건드리지 않는다.
- **스트리밍 응답**: 백엔드가 `chat()` 완료 후 한 번에 반환하므로 토큰 단위 스트리밍 불가.
  체감 속도는 로딩 상태 설계로 해결한다.
- **서버 측 대화 저장**: 백엔드에 세션/DB가 없다. localStorage로만 처리한다.
- 멀티 대화방(스레드) 관리, 사용자 인증/계정, 파일·이미지 업로드, 음성 입력.
- RAG / 임베딩 검색 (`bge-m3`는 목록에서 제외 대상).
- 배포·CI 구성.
- TypeScript 전환 (현재 JS 프로젝트 유지).

## 6. 설계 고려사항 (Design Considerations)

### 설계도와 달라지는 점 (의도적 개선)
원본 `chat_ui_설계도.jpg`는 좌측 설정 사이드바 + 우측 채팅의 2단 구조다.
정보 구조는 유지하되 아래를 개선한다:

| 설계도 | 변경 | 이유 |
|---|---|---|
| 설정이 항상 펼쳐진 사이드바 | 기본 접힘 / 필요 시 열기 | 채팅이 주인공, 설정은 보조. 모바일에서 사이드바는 화면을 잡아먹음 |
| 입력창 placeholder가 "대화 초기화" | "무엇이든 물어보세요" | 설계도의 명백한 오기. placeholder는 입력 유도여야 함 |
| 버튼 라벨 "응답 생성 중..." | 버튼은 상태에 따라 전송/중단 | 로딩 중 취소 수단이 없으면 사용자가 갇힘 |
| 기본 시스템 폰트 조합 | 의도된 타이포 스케일 | 템플릿 티를 벗기기 위함 |
| 카드 위 카드 + 균일 그림자 | 계층에 따른 구분 | 전형적인 "생성된 페이지" 신호 회피 |

### 시각 방향
- 톤: 로컬에서 도는 도구다운 차분함. 과장된 그라디언트·장식 금지.
- 강조는 한 곳에만 (전송 액션 / 활성 모델 표시).
- 페이지 로드 애니메이션 남발 금지. 모션은 사용자 행동에 대한 응답으로만.
- 구체 팔레트·타이포는 구현 단계 진입 전 `frontend-design` 스킬 지침에 따라 확정한다.

### 기술 구조
설계도의 데이터 흐름(`image-1.png`)을 따른다:

```
ChatInput → ChatWindow(state) → chatApi.js → FastAPI → Ollama
                     ↑                          ↓
                MessageList ←──── 응답 ────────┘
```

- `src/api/chatApi.js` — fetch 래퍼, 타임아웃/취소/에러 정규화
- `src/components/` — ChatWindow, MessageList, MessageBubble, ChatInput, SettingsPanel
- `src/hooks/useChat.js` — 메시지 상태·전송·취소 로직
- 상태 관리 라이브러리 추가 없음 (React 내장 훅으로 충분)

## 7. 기술 고려사항 (Technical Considerations)

- **기존 스택 유지**: React 19.2 + Vite 8. 새 프레임워크 도입 없음.
- **의존성 추가 최소화** (ponytail 사다리 적용):
  - 상태관리 라이브러리: 불필요 → 추가 안 함
  - CSS 프레임워크: 불필요 → 순수 CSS + CSS 변수
  - 마크다운 렌더러: 코드블록·줄바꿈만 필요하면 자체 처리로 충분.
    전체 마크다운이 필요하다고 판단되면 그때 `react-markdown` 추가하고 이유를 남긴다.
- **API 베이스 URL**: `http://127.0.0.1:8000` 하드코딩 대신
  Vite 프록시 또는 `VITE_API_BASE` 환경변수로 분리.
- **CORS**: 백엔드가 `allow_origins=["*"]`이므로 직접 호출도 동작한다.
- **타임아웃**: 로컬 7B 모델은 첫 토큰까지 수십 초가 걸릴 수 있다.
  타임아웃을 짧게 잡으면 정상 요청을 죽인다. 넉넉히(120s) 설정한다.
- **백엔드 응답 필드명 주의**: `message`(AI 답변), `model`, `elapsed_time` 세 개뿐이다.
  설계도 주석의 `ai_message` / `걸린시간`은 실제 계약이 아니다.

## 8. 성공 지표 (Success Metrics)

1. 백엔드 실행 상태에서 질문 → 답변까지 오류 없이 왕복한다.
2. 모델을 바꿔 같은 질문을 보내면 응답의 모델명이 실제로 바뀐다.
3. 백엔드를 끈 상태에서 전송하면 원인과 해결법이 담긴 오류가 뜬다 (무반응 금지).
4. 새로고침 후 대화와 설정이 복원된다.
5. 360px 폭에서 레이아웃이 깨지지 않는다.
6. 키보드만으로 전송·모델 변경·초기화가 가능하다.
7. `pnpm build`와 `pnpm lint`가 통과한다.
